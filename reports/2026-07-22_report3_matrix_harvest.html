1 · The gap

Two fixed things, one of them still serial

After Report #2 the entity harvest ran four lanes concurrently — but it was still four specific topics, each seeded by a hand-maintained reports/awesome-lists/awesome_<topic>.md. There was no way to ask for, say, agents in healthcare: no curated list exists, and nothing in the pipeline expressed the idea of a category at all.

The second gap was quieter. Query expansion was never parallelised. Stage 1A (scripts/run_stage1.sh) expands every seed topic in a single claude call and writes one shared state/search_strategy_db.json — precisely the monolith-plus-shared-mutable-file shape that Report #1 identified in the harvest and Report #2 removed. It survived untouched because the earlier work only followed the harvest path.

i and j are 1-based indices into the lists as typed — that is the entire meaning of the filenames, and it makes list order load-bearing: reordering --categories renames every cell. Nothing downstream has to infer anything, because state/matrix/manifest.json records the index-to-name mapping and every cell file repeats its own category and topic inside.

Each cell owns every file written for it. That is the same ownership argument as the BuildingBlocks shards, applied one dimension up — not a new mechanism:

Every transient file is dot-prefixed, so one rule — state/matrix/.* — covers them all. That was verified with git check-ignore against thirteen real filenames rather than assumed: all four kept outputs tracked, all nine transient patterns ignored.

3 · Both phases parallel, no barrier

Each lane expands and harvests its own cell
lane 1:1  ── expand ──▶ harvest ──────────────▶ done
lane 1:2  ── expand ──────▶ harvest ──────────────▶ done
lane 2:1  ── expand ─▶ harvest ──────────▶ done
lane 2:2  ── expand ────────▶ harvest ────────────────▶ done
             ▲ all expansions run concurrently
                          ▲ a cell starts harvesting on ITS OWN expansion

Chaining inside the lane is what makes it “each by each”: cell 2:1 begins harvesting the moment its own expansion finishes, rather than waiting at a global barrier for the slowest expansion in the run. --phased restores that barrier for when you want to read every query set before committing harvest budget.

The per-cell expander is Stage 1A scoped down: one intersection, one file only that cell writes. Queries must be about the topic as applied to the category — a generic tool with no connection to the category does not belong in the cell, and neither does a category resource unrelated to the topic.

4 · Four invariants, enforced in code

Not asked of the model — taken away from it
InvariantWhy a prompt is not enough
Identity is stamped from the manifest. Every harvested entity's topic and category are overwritten from manifest.json before the merge.Unlike the four fixed topics, category is a label this pipeline assigns to a cell, not a property the model discovers. The manifest is authoritative by definition, so there is no judgement to defer. The test mock deliberately emits WRONG-TOPIC/WRONG-CATEGORY on every extraction; assertions D2–D4 confirm neither ever reaches a cell file.
Expansion can never shrink. A result holding fewer queries than already existed is rejected outright.The prompt says “preserve existing rows”; a prompt is not a guarantee. A model returning a fresh short list would otherwise destroy expansion work that has already been paid for.
No query set, no harvest. Harvesting a cell with no expansion is a hard error.The alternative is falling back to the model choosing its own scope — exactly the uncontrolled sourcing the matrix exists to prevent.
Concurrency is capped. MAX_PARALLEL (default 4) bounds in-flight lanes; STAGGER_SEC spaces the starts.A 4×5 matrix is 20 cells. Twenty simultaneous model lanes would exhaust the account session limit in minutes and fail together — the opposite of what parallelism is for.

Input is validated the same way. Duplicate or case-variant names are refused, not deduped: two identical categories would harvest the same thing into two cells, and the duplicated work would read as real coverage in the summary.

5 · Two bugs, both found by running it

Neither was visible in review
1

The bounded-concurrency pool was unsound

Two plausible implementations are both wrong on this workload, and I wrote one of them first:

  • kill -0 $pid cannot detect a finished lane. An exited background child stays a zombie until it is waited on, and its process entry still exists — so kill -0 keeps reporting it alive forever and the pool never refills.
  • wait -n unblocks on the first exit but does not say which child it was, and it reaps that child — so the later wait <pid> used to recover the exit code returns “no such job” instead.

Fix: drive the pool from jobs -rp, which lists only still-running children. A pid that has dropped off that list is finished and can be waited on exactly once for its true status. Assertion F9 confirms a capped pool of 4 finishes the same workload faster than a pool of 1 — i.e. that the pool actually refills rather than stalling.

2

This platform's jq emits CRLF, and it reached filenames

The manifest on disk is clean, but jq -r on this build terminates lines with \r\n. read strips only the \n, so a trailing carriage return survived in the last field only:

$ jq -r '.cells[0] | [...] | @tsv' manifest.json | cat -A
1^I1^Ihealthcare^Iagent^Icategory#1_topic#1^M$
                                            ^^ carriage return

read  → cid = "category#1_topic#1\r"   len 19   ← corrupted
$(…)  → cid = "category#1_topic#1"     len 18   ← clean

Invisible in normal output, but CELL_ID feeds the per-cell log filename and the run summary, so lanes were writing logs with a control character in the name. Command substitution strips it, which is why only the @tsv read loops were affected — and why the harvests themselves still worked: the orchestrator passes i/j to the children, which re-derive the id via $(…).

Fix: IFS=$'\t\r' in both read loops, with a regression assertion (F2b) that the plan output contains no carriage return, and F8b that exactly one cleanly-named log file exists per cell.

The bug that wasn't. An early test run showed every cell file containing one foreign-topic row. That turned out to be the test mock inferring the topic from prose that also appears in the appended 1G system prompt — but it is the same class of failure the entity harvest's topic guard was added for, and it is why identity here is stamped from the manifest rather than merely validated. Recorded because a fixed test is not evidence that the concern was imaginary.

8 · The union view

And the identity decision inside it

merge_matrix.sh folds the cell files into state/matrix/matrix_union.json — derived, single-writer, under a lock, idempotent, with the cell files staying authoritative. One decision there is worth stating explicitly:

Identity across cells is (category, topic, name), not the topic|name entity_key used inside a cell. Two cells sharing a topic legitimately hold the same tool — “this matters for healthcare agents” and “…for finance agents” are two findings, not a duplicate. Collapsing them on entity_key would silently drop one, and the loss would look like successful dedup. Assertions G5 and G6 pin this.

A missing cell file is fine — not every cell has been harvested. A cell file that is present but invalid aborts the fold rather than being skipped.

9 · Honest limits

  • List order is load-bearing. Reordering --categories renames every cell. Use --harvest-only, which reuses the stored manifest, rather than retyping lists for a follow-up run.
  • Cost scales with cells, not lists. An n×m matrix is n·m harvests. Use --dry-run first and start with a small --target.
  • Parallelism does not raise the quota ceiling — it consumes it faster. MAX_PARALLEL is the throttle; raise it only with headroom to spare.
  • Not exercised against live model calls. Every run here used a deterministic mock. Ownership, locking, identity stamping, pool behaviour and fold semantics are structural and fully covered; whether expansion produces good queries for a given intersection is not something these runs can speak to.
  • Query quality is unmeasured. The no-shrink rule protects the query set's size, not its usefulness. Yield counts are stamped back per loop, but nothing yet prunes low-yield queries the way Stage 1D does for the seed topics.

10 · Conclusion

The harvest is no longer limited to four hand-curated topics: any (category, topic) intersection you can type becomes a cell that owns its files and runs alongside the others, and query expansion — the last monolithic, shared-file, serial stage — is now per-cell and parallel with the rest. The invariants that matter are enforced in code rather than requested in prompts, and the concurrency cap is deliberate quota protection, not an oversight. Both defects found were in the parts that only exist because of concurrency, and both were invisible until the system actually ran — the same lesson as Report #2, arrived at independently.
