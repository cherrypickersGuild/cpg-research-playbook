INCIDENT ANALYSIS · ENTITY REGISTRY

GitHub stars: why 55% of eligible repos have none

The registry holds 549 entities whose target_url is a GitHub repository. Only 242 carry a star count. The received explanation is "the unauthenticated 60/hour rate limit." The run artifacts on disk say otherwise — and the real cause is more interesting.

SUBJECT scripts/github_meta.py · harvest_entities.sh COMMITS 8e74412 → a3ff811 → 77c7f01 DATE 2026-07-17
Diagnosis

Not a rate limit. An ordering bug: the fetcher runs before the URLs it needs exist.

The prefetch reads target_url from the candidate batch — but at that moment most candidates carry the literal string "unknown", because the pipeline deliberately defers URL resolution to the model in the next step. The fetcher finds no repositories, fetches nothing, and hands the model an empty file. The model then dutifully writes github_stars: null.

The blanks are not obscure projects. Missing star counts include modelcontextprotocol/servers and jlowin/fastmcp — two of the most-starred repositories in the entire MCP ecosystem. Any ranking, prioritisation, or "top N by popularity" cut over this registry is currently reading mostly nulls.

2 · What the run artifacts prove

Each harvest writes a sanitized metadata file for the model to read. Three survive on disk. They are the whole case.

  "generated_at": "2026-07-14T13:16:02Z",
  "mode": "unauthenticated",
  "rate_limit": { "limit": null, "remaining": null, "reset": null },   <- no API call was EVER made
  "rate_limited": false,                                        <- not rate limited
  "repos": {}                                              <- found zero repositories

The prompt run's file is byte-identical in shape (206 bytes, empty repos). The skill run's file is the only substantial one: 30 repos, 29 ok.

Read those three fields together. rate_limited: false and every rate_limit number null means the code never issued a single HTTP request — a rate limit leaves fingerprints (limit: 60, a remaining count, a reset timestamp). There are none. The fetcher didn't fail, didn't get throttled, didn't time out. It looked at the candidate batch, found nothing that parsed as a GitHub repository URL, and correctly exited having done nothing. The rate limit is not the cause. Zero work was attempted.

3 · The main reason — resolution happens after the fetch

The harvest loop runs three steps in this order. Step 1 emits URLs, step 2 fetches metadata for them, step 3 resolves the URLs. Steps 2 and 3 are the wrong way round.

1
Candidate sourcing — harvest_entities.sh:330 Asks the model for source_url + a best-effort target_url, and explicitly instructs: "If you cannot confidently determine target_url, emit the literal string "unknown" rather than guessing — Stage 1G will try to resolve it separately via WebFetch."
2
GitHub prefetch — harvest_entities.sh:425 github_meta.py prefetch --hits $BATCH_HITS reads target_url from those hits and calls parse_repo() on each. parse_repo("unknown") → None. Every deferred candidate is silently skipped. repos = [] → no requests → GH_META = {"repos":{}}.
3
1G entity extraction — harvest_entities.sh:442 Now the model resolves target_url via WebFetch — this is where github.com/owner/repo finally appears. It is then told: "look up its lowercase owner/repo in $GH_META's .repos… otherwise (missing entry, non-ok status, non-repo target_url…) set github_stars: null — never estimate it from a page." The entry is missing, because step 2 ran before the URL existed. → null.

The model behaves perfectly. The instruction is precise, the fallback is safe, and the anti-fabrication rule ("never estimate it from a page") is exactly right. The data simply cannot arrive in time. A repository whose URL the model discovers can never receive a star count — only repositories already resolved in the candidate batch are eligible, and by design the candidate step is allowed to defer.

Why mcp is the healthiest topic — the irony at the centre of this. Before commit 77c7f01, the model fetched api.github.com itself, after resolving target_url. The order was right; the mechanism was wrong (60/hr exhaustion, and per a3ff811 a rate-limit prose deferral that collapsed to [] and crashed the ledger merge). The fix corrected the mechanism — deterministic, cached, sanitized, token-ready, non-fatal — and in moving the fetch outside the model, moved it upstream of the resolution step that produces its input. The new path has the right mechanism and the wrong order. mcp scores best because it was harvested under the old, broken-but-correctly-ordered path.

4 · The contributing reason — no token

The ordering bug explains the empty runs. It does not explain everything: the skill run did find 30 repositories and fetched 29 successfully. Its metadata file records how close that came to the ceiling:

state/harvest_skill_github_meta.json
  mode:         "unauthenticated"
  rate_limited: false
  rate_limit:   { "limit": 60, "remaining": 5, "reset": 1784093733 }   <- 5 requests from the wall

Neither GITHUB_TOKEN nor GH_TOKEN is set in this environment, so github_meta.py runs in its bounded unauthenticated mode: live_budget = max_unauth (default 50) per batch, against GitHub's 60 requests/hour for anonymous callers. With BATCH_SIZE=40, a single well-resolved batch can consume most of an hour's quota. The deterministic cache — which is working correctly and reuses fresh entries for free — holds just 86 repositories, of which only 77 correspond to eligible entities. The fetcher has seen 14% of the repos it should have.

So the two causes stack: the ordering bug means most repositories are never offered to the fetcher, and the missing token means the few that are offered exhaust the quota quickly.

5 · Solution

Three layers, in the order worth doing them. The first two are cheap and need no re-harvest.

A · Set a token 2 minutes · 83× headroom

The fetcher already supports this fully and securely — env-only, Authorization header, never logged, never cached, never passed to the model. Nothing to build:

# PowerShell — session scope
$env:GITHUB_TOKEN = "ghp_..."      # a bare public-read PAT; no scopes needed

Unauthenticated 60/hr → authenticated 5,000/hr. All 549 eligible repositories become a single sub-minute pass instead of a ten-hour drip.

B · Backfill the existing registry no re-harvest needed

This is the key insight, and the merge layer was already built for it. From merge_entity_registry.sh:108:

github_stars: latest non-null measurement always wins — not identity data, so unlike target_url no conflict log is needed. scripts/merge_entity_registry.sh, line 108

Star counts are freshness data, not identity data. That means a standalone pass may repair all 307 blanks at any time without re-running discovery, re-fetching pages, or touching the ledger. The 549 target_urls are already resolved and sitting in the registry — the hard part is done. There is even a precedent to copy: scripts/backfill_entity_target_url.py, added in daa5162 for exactly this shape of repair.

# the shape of the fix — reads the registry, not the hits
scripts/backfill_entity_github_stars.py \
    --registry state/entity_registry.json \
    --cache    state/github_meta_cache.json      # reuses the 86 already cached

With a token this is one pass over 549 repos; the existing cache covers 77 for free, and is_fresh() keeps repeat runs nearly free within its 7-day window.

C · Fix the ordering so new harvests self-populate the real repair

Backfill treats the symptom every run. To stop the bug recurring, the fetch must happen after resolution. Two viable shapes:

OptionHowAssessment
Second prefetch pass
smaller change		Keep step 2 as-is (it still catches pre-resolved candidates). After 1G emits its batch, run github_meta.py prefetch again with the batch output as --hits — its target_urls are now real — then patch github_stars into the batch before the merge.Fits the existing flow; _repos_from_hits() already reads target_url, so the batch output needs no reshaping. Requires one new deterministic step between 1G and merge.
Take stars out of the model entirely
cleaner		1G never sets github_stars (always null). A deterministic post-step owns the field end-to-end, exactly as option B's backfill does — just wired into every loop.Better separation: the model resolves and describes, the script measures. Removes ~120 words of star-handling instruction from the 1G prompt and deletes a whole class of model-compliance risk. The merge's "latest non-null wins" already makes this safe.

Recommendation: option B now, option C-second later. The backfill script is the same code either way — write it once for the repair, then call it per-loop to make the pipeline self-healing. Option A is a prerequisite for both being fast.

D · Make the failure loud

The deepest problem is not the null stars — it is that this ran three times, wrote a 206-byte file each time, and said nothing. The prefetch is deliberately non-fatal so "a metadata hiccup cannot abort the harvest," which is correct. But silent and non-fatal are different things:

  • Warn on the impossible-looking case. If $BATCH_HITS contains any github.com string but repos_seen == 0, log a warning. That single check would have surfaced this on 2026-07-14.
  • Log the coverage ratio per loop — repos_seen, fetched, from_cache, rate_limit_remaining are already in the JSON summary that prefetch prints; it goes to $ERR_LOG and nothing reads it.
  • Warn when mode == "unauthenticated" at harvest start — one line, tells you the run has 60 requests for the hour.
  • Add a regression test alongside tests/test_harvest_github_cache.sh: hits carrying target_url: "unknown" whose entity resolves to a repo root must still end with a non-null github_stars. That test fails today and would pin the fix.

6 · Correcting the record

The standing explanation for this is wrong, and worth updating wherever it is written down. "The MCP 1G star-fetch exhausts GitHub's 60/hr limit; it needs a token" was an accurate description of the old in-model path, and it is why 77c7f01 was written. It has not been the failure mode since 2026-07-13. Today the fetcher makes zero requests on most runs and never reaches the rate limit at all. A token is still needed — but a token alone would not have moved the agent or prompt coverage by a single entity, because those runs never issued a request to be throttled.
