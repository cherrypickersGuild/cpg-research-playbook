The one finding everything reduces to

The discovery net worked. Every quality mechanism the project designed lives in stages that never ran.

The project has two halves. The discovery half — harvesting entities and cases — is complete, tested, and pushed: 1,161 entities and 231 cases sit on disk. The vetting half — validate, select, build the deck — exists only as specifications, three of them uncommitted on a single machine, and none of it has ever executed.

Low-tier sources, the misleading "verified" label, the empty validation gate, the missing star counts — each is the same story: a safeguard that was designed and written, then never switched on. The remedy is not more harvesting. It is turning on the vetting that already exists, after pointing it at better inputs.

Section 1

The task began as "compare axCaseResearch4 with cpg-research-playbook." They are not two projects.

axCaseResearch4 is the local working copy of the GitHub repository cherrypickersGuild/cpg-research-playbook — it is that repo's origin, and both point at the same commit. There is no content divergence on main: zero commits ahead or behind, zero modified tracked files.

The meaningful difference is not between the two — it is between what is committed and what only exists locally: 63 untracked files and one unpushed commit. Most is disposable scratch, but four files are not — and they matter more than all the rest.

The best-tested, fully-backed part of the project is the replaceable harvest corpus; the irreplaceable design work has no backup at all.

Section 4

"Verified" does not mean verified

The single most misleading number in the corpus.

The registry reports 208 verified cases. In the extractor's schema, verification_status has exactly two legal values:

"verified" = description pulled from the page itself  ·  "snippet-only" = page couldn't be fetched agents/stage1/ax_case_harvest_extractor.md, lines 79–80

verified means the HTTP fetch succeeded. It says nothing about whether the company is real, the KPI is true, the source is independent, or the claim was later retracted. "208 verified" means "208 pages loaded."

By the project's own rule, zero cases are verified. 01_case_finder.md line 44 defines it: "a KPI counts as verified only if it traces to Tier A, Tier B primary financials, or two independent sources." In the corpus: 0 Tier-A sources, 0 multi-sourced cases (all corroboration_count = 1), 0 Tier-B primary financials. The label and the definition are unrelated words that happen to be spelled the same — and only one of them is in the data.

Section 5

Why every source is low-tier

Not bad luck in what surfaced — the deterministic output of the seeds and a tier-blind harvest.

Zero of 231 cases have an independent Tier-A outlet (no Reuters, WSJ, FT, Bloomberg, HBR, MIT Sloan). ~62% are company self-published engineering blogs; the rest are vendor pages and open platforms (Medium, LinkedIn). Three causes stack:

  1. The seed sets the ceiling. The primary AX seed crawls genai-llm-ml-case-studies — described in the crawl report as "500+ case studies with links to the original engineering blog posts." A directory of self-published blogs has a hard tier ceiling of B/D; it contains zero independent outlets to find.
  2. The harvest is tier-blind. harvest_ax_cases.sh never mentions "tier"; the extractor's only mention is the line disclaiming it ("no source-tier classification"). Nothing prefers, requires, or records source independence.
  3. The resolver pushes down-tier. The candidate prompt says resolve to "the company blog post"; paywalls drop the independent outlets that live behind them; there is no corroboration pass.
Proof it is the pipeline, not the world: the secondary seed did contain higher-tier hits — HBR (Tier A, ×2), Deloitte (×3), Gartner (×2). Traced seed → registry, all were dropped; only 2 McKinsey (Tier C) survived. The pipeline didn't just fail to find Tier A — it discarded the Tier A it was handed.

The deepest reason is a real domain skew: AX stories genuinely live mostly on company blogs, and independent coverage is scarcer and paywalled. 01_case_finder.md was designed precisely to counteract this ("start Tier A/B, verify upward, never let a vendor page be a sole source"). The harvest is that design with every countermeasure removed.

Section 6

Is the validator redundant?

A fair question — the case finder tiers sources and checks KPIs, and the validator does it again.

Answer: not redundant. Against the pipeline that actually ran, it is the only validation that exists. The apparent overlap is with 01_case_finder.md, which never ran and holds zero cases. All 231 cases came from the harvest extractor, which explicitly disclaims source tiering, KPI verification, and contradictory-evidence search. Remove the validator and nothing performs those checks at all.

The architecture you actually have — a cheap wide net, then one rigorous gate — is sound, arguably better than the rich finder, because the validator derives tier and contradictions itself rather than trusting upstream. One caveat: it filters, it cannot manufacture. Validating the current 231 without fixing seeds first yields a correctly-labelled pile of low-tier cases and a near-empty main deck. Fix sources first (section 5), then gate.

Section 7

The GitHub-stars collection bug

A separate, self-contained defect in the entity harvest.

Of 549 entities whose target_url is a GitHub repo, only 242 carry a star count — 307 are blank, including flagship repos like modelcontextprotocol/servers. The received explanation ("the 60/hour rate limit") is wrong for the current code.

The real cause is an ordering bug. The metadata prefetch reads target_url from the candidate batch — but at that moment most candidates carry the literal string "unknown", because URL resolution is deliberately deferred to the next step. The fetcher finds no repositories, makes no request, and hands the model an empty file; the model then correctly writes github_stars: null. The run artifacts prove no request was ever attempted:

# state/harvest_agent_github_meta.json — 206 bytes
"rate_limited": false,   "rate_limit": { "limit": null, "remaining": null, "reset": null },   "repos": {}

A real rate limit leaves limit: 60 plus a remaining count and a reset timestamp. All null means zero requests. Ironically, mcp — harvested under the old in-model path — has the best coverage (56%), because that path fetched after resolving the URL. Commit 77c7f01 fixed the mechanism and, in moving the fetch outside the model, moved it upstream of the step that produces its input.

The good news: repair needs no re-harvest. merge_entity_registry.sh treats stars as freshness data — "latest non-null measurement always wins." A standalone backfill over the 549 already-resolved URLs fixes all 307 blanks. Set GITHUB_TOKEN first (60 → 5,000 req/hr), then either re-order the fetch (after resolution) or take stars out of the model entirely.

Section 8

Recommendations, in priority order
  1. Commit the four deck-stage files. 02_validator.md, 03_selector.md, 04_slide_builder.md, .claude/agents/ax-validator.md. 32 KB of finished design with no backup, on one machine — the cheapest work to protect is currently the least protected. Also gitignore state/_* and .scratch_ax/ so scratch stops hiding real files. §1
  2. Fix the AX seeds and invert their priority before any re-harvest — add Tier-A-first sources (HBR/MIT Sloan archives, Reuters/Bloomberg desks, SEC EDGAR) so the pipeline can source what the validator will later demand. Sourcing quality is set upstream; nothing downstream can add it back. §5
  3. Backfill GitHub stars from the registry. Set GITHUB_TOKEN, run a standalone pass over the 549 resolved URLs — no re-harvest, because the merge takes the latest non-null value. Then re-order the fetch so new harvests self-populate. §7
  4. Bridge harvest → pipeline, then run the validator. Feed the 231 cases into ax_case_db.json (or repoint Stage 2 at the harvest registry), then let the gate run. Expect heavy, correct attrition — 6–10 main-deck cases from 231 is the designed yield, not a failure. §3, §6
  5. Rename verification_status to say what it means — e.g. fetch_status: fetched | snippet_only — and report a separate source-tier stat, so the corpus stops looking stronger than its sources justify. §4
The order matters. Items 1 and 3 are safe housekeeping. Item 2 must precede item 4 — validating before fixing the seeds only labels the problem. The end state is a smaller, source-verified, gated set feeding a deck — which is exactly what the pipeline was designed to produce, once its unused half is switched on.
