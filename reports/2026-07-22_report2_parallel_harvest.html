1 · The change in one line

Give every lane a file it owns; make the union derived

No locking was bolted onto the shared registry. The shared registry stopped being shared:

BEFORE                                  AFTER
  agent ─┐                                agent  → BuildingBlocks_Agent.json  ─┐
  mcp   ─┼→ entity_registry.json          mcp    → BuildingBlocks_MCP.json    ─┤
  prompt─┤   (4 concurrent writers,       prompt → BuildingBlocks_Prompt.json ─┼→ merge_building_blocks.sh
  skill ─┘    read-modify-write)          skill  → BuildingBlocks_Skill.json  ─┘      (1 writer, after)
                                                                                            ↓
                                                                              entity_registry.json (derived)

Shards use the identical schema to the union, so every existing jq query, the --check tally and the merge logic work on them unchanged. The same treatment was applied to the other two contended files: the visited-URL ledger and the GitHub-metadata cache are now per-topic as well.

3 · Findings from testing

Three defects, all surfaced by actually running it

The unit assertions passed on the first attempt. Every one of these was found by the two end-to-end runs, which is the argument for doing them.

1

The fold hard-failed when no shard existed — breaking a previously-passing run

Symptom: test_harvest_targets.sh started failing its “all stages already at target → exit 0” assertion. When every lane is already complete, no lane runs, so no lane bootstraps a shard — and the new fold step then aborted, turning a clean run into exit 1.

Fix: a missing shard is now derived from the union rather than treated as an error. This is provably lossless — the shard is filled with exactly the union's rows for that topic, so folding it back is a no-op — which is why it is safe as the default. --strict preserves the demand that every shard already exist. A shard that exists but is malformed is still always fatal: that cannot be repaired without guessing.

2

One stray row poisoned a shard and blocked the fold for all four topics

Symptom: in the first end-to-end run every shard ended up with one entity carrying a topic other than its own, and the fold refused all four:

ERROR: shard BuildingBlocks_Agent.json contains 1 entity whose topic != 'agent'
ERROR: shard BuildingBlocks_MCP.json   contains 1 entity whose topic != 'mcp'
…
RESULT: union fold FAILED — harvest INCOMPLETE.

The trigger was a flaw in the test's mock, but it exposed a real gap: merge_entity_registry.sh merges whatever topic it is handed. Harmless when one registry held every topic — structurally unsafe now that shard disjointness is the invariant the whole parallel design rests on. A single mislabelled row from the extractor would take down the union rebuild for every topic at once.

Fix: a topic guard in harvest_entities.sh, applied at the lane boundary before the merge, where the correct topic is known for certain. Foreign-topic rows are dropped and named on stderr. Dropping rather than relabelling is deliberate: a row the extractor labelled mcp while working the agent seed list is a row whose content is suspect, not just its label — silently rewriting .topic would launder a model error into the corpus. Covered by 5 new assertions (FT1–FT5).

3

Two existing tests encoded the old single-file layout

Symptom: test_harvest_1g_shape_guard.sh counted merged entities in entity_registry.json, and test_harvest_github_cache.sh seeded github_meta_cache.json — both paths a lane no longer writes.

Fix: repointed at the shard and the per-topic cache. Genuine test updates, not assertions weakened: each still asserts exactly what it did, against the file that now holds the answer.

One non-finding, recorded for honesty. An early run showed each lane adding only one entity and then stopping. That was the test mock keying its counter off the candidate-sourcing call, which is the one call whose prompt does not name the topic — so all four lanes shared a counter and the extractor re-emitted the same record every loop. The harvester's no-progress detection, dedup and honest “target NOT met” stop all behaved correctly throughout. Mock fixed; no product change.

Between half and two-thirds of all merged rows vanished under the old layout — silently, with every merge reporting success and the file remaining valid JSON throughout. That is the lost-update failure mode from Report #1 §6, reproduced on demand. The shard run lost nothing, in either execution.

The assertion in the suite is one-directional: sharded is never worse than shared. It never demands that the shared run must lose rows — a race that happens not to collide on a fast machine would make that a flaky test.

7 · How to run it

# concurrent, all lanes + AX, then one fold
bash scripts/harvest_parallel.sh

# a subset, or entity topics only
bash scripts/harvest_parallel.sh --topics agent,mcp
bash scripts/harvest_parallel.sh --entities-only
bash scripts/harvest_parallel.sh --dry-run       # show the launch plan, run nothing

# or one lane per session — the lane locks make this safe with no orchestrator
bash scripts/harvest_entities.sh agent           # session A
bash scripts/harvest_entities.sh mcp             # session B
bash scripts/merge_building_blocks.sh            # once, when both are done

Per-lane console output lands in state/logs/parallel_<run_id>/<lane>.log; interleaving five lanes onto one terminal is unreadable. Lanes start 20 s apart by default — four cold model calls in the same instant is the shape most likely to trip the session rate limit, which fails every lane at once and would defeat the isolation this design exists for.

8 · Honest limits

  • The speedup is bounded by the slowest lane, not the average. If one topic has far more remaining work, parallelism buys correspondingly less.
  • The session rate limit is untouched by this work. Four concurrent lanes consume quota four times faster. Staggered starts and per-lane failure isolation reduce the blast radius; they do not raise the ceiling. A lane that hits it fails alone, is reported INCOMPLETE, and the fold still runs — but it will still fail.
  • Locks are advisory. They bind the scripts that call them, not a human running jq > file by hand.
  • Ledger shards are transient (gitignored). Crawl history survives only because the fold merges them back into the committed union ledger — so run the fold, or a lane's visited-URL knowledge is lost and pages get re-crawled next run. Both orchestrators do this automatically; a manual multi-session run must not skip it.
  • The AX lane was already parallel-safe alongside the entity lanes — it touches neither the ledger nor the entity registry. It gained only a self-collision lock.
  • Not verified against live model calls. Every run here used a deterministic mock. The concurrency, fold and locking guarantees are structural and fully exercised; real-world extraction quality under concurrent load is not something these runs can speak to.

9 · Conclusion

The bottleneck identified in Report #1 is removed, and removed by construction rather than by coordination: there is no lock protecting the entity registry during a harvest because no harvest lane writes it any more. Concurrent merges now preserve 48/48 rows where the previous layout silently discarded a third to two-thirds of them, measured wall-clock falls 2.90× on identical work with identical output, and the 1 161-entity production corpus migrated with zero records altered. Three defects surfaced during testing and all three are fixed and covered — two of them only became visible when the system was actually run end to end, which is the strongest argument in this report for having done so.
