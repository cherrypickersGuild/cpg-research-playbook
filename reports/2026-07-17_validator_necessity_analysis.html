Is 02_validator.md redundant?

The case finder already tiers sources, checks KPIs against them, and searches for contradictory evidence. The validator does the same things again. That looks like duplicated work — so the question is fair. The answer depends entirely on which upstream you compare it to, and the corpus on disk settles it.

COMPARES 01_case_finder.md · ax_case_harvest_extractor.md · 02_validator.md EVIDENCE 231 cases in ax_case_harvest_registry.json DATE 2026-07-17
Verdict

Not redundant. Against the pipeline that actually ran, it is the only validation that exists.

The real overlap is with 01_case_finder.md — which has never run and produced zero cases. Every one of the 231 cases on disk came from the harvest extractor, a spec that explicitly disclaims source tiering, KPI verification, and contradictory-evidence search. Remove the validator and nothing in the system performs those checks at all.

The gate. Seven checks, then gate_passed. Uncommitted, local-only, and the file CLAUDE.md declares mandatory before any case reaches a slide.

The harvest extractor says so itself — this is not an inference:
"This is deliberately a lighter-weight sibling of the full case-finder pipeline — no KPI baseline/after/delta breakdown, no source-tier classification, no contradictory-evidence search. Speed and volume over exhaustive rigor; a harvested case can be promoted into the rich pipeline later by a human if it's strong enough." agents/stage1/ax_case_harvest_extractor.md, lines 8–12

The lean path was designed as a net, not a filter. It was always meant to hand off to something stricter. The validator is that something.

The word "verified" is doing dangerous work

The registry reports 208 verified cases. That number invites a reading it cannot support. In the extractor's schema, verification_status has exactly two legal values, and here is what they mean:

"verified" = description pulled from the page itself
"snippet-only" = page couldn't be fetched, description is the search snippet agents/stage1/ax_case_harvest_extractor.md, lines 79–80

verified means the HTTP fetch succeeded. Nothing more. It is a plumbing flag. It makes no claim about whether the company is real, the KPI is true, the source is independent, or the story has since been retracted. "208 verified cases" means "208 pages loaded."

Test it against the project's own rule. 01_case_finder.md line 44 defines verification precisely: "a KPI counts as verified only if it traces to Tier A, Tier B primary financials, or two independent sources." Applied to the corpus on disk:
  • Tier A independent outlets — 0 of 231
  • Two independent sources — 0 of 231 (every case has corroboration_count = 1)
  • Tier B primary financials — 0 of 231 (the Tier B present is engineering blogs, not filings)

By the project's own definition, zero of the 231 KPIs are verified — while 208 carry the label "verified". The two uses of the word are unrelated, and only one of them is in the data.

Where the redundancy genuinely is

To answer the question honestly rather than defensively: yes, there is real duplication — but it sits between 01_case_finder and 02_validator, not between the harvest and the validator. Both specs independently define source tiers, the KPI-verification rule, contradictory-evidence search, and date-window handling. If 01_case_finder ran exactly as written, the validator would repeat perhaps a third of its work.

Three things make that duplication worth paying for anyway:

  • The finder has a quota; the validator has none. 01_case_finder.md sets target_case_count: 200 and instructs "never pad the count." That is an agent asked to hit a number while also judging whether its own findings qualify. The validator has no target and no stake in the answer. This is separation of duties — the same reason auditors re-test what accounting already tested. Overlapping checks under different incentives are not redundant.
  • They check at different times. The finder checks a URL when it discovers it; the validator re-checks it when the deck is being built. Between harvest (2026-07-15) and a presentation, links rot, articles move behind paywalls, and claims get walked back. A URL verified in July is not a URL verified in October.
  • Only the validator knows there is an audience. Deck-readiness, Samsung relevance, appendix routing, and the gate_passed boolean have no counterpart upstream. Neither upstream spec has any concept of the deck.

And the decisive point: this trade-off is hypothetical. 01_case_finder produced nothing. ax_case_db.json is {"cases": []}. The duplication being worried about has never once occurred.

The architecture you actually have is the better one

Harvest-wide-then-validate-once is a sound design — arguably better than the rich finder. A cheap net over 231 candidates followed by one rigorous gate concentrates the expensive work (URL fetching, tier classification, adversarial search) in a single auditable place, instead of scattering it through a discovery agent that is also being asked to hit 200.

It also composes well, because the validator derives what the harvest omits rather than trusting it:

The one thing standing in the way is plumbing, not design. The validator's declared input is ax_case_db.json in the finder's rich schema (source[] with tiers, kpi[] with baseline/after/delta). The harvest registry is flat: source_url as a string, kpi_value as free text like "3 days -> same-day". An adapter — harvest record → validator input — is the missing piece, and it is small because the validator re-derives most of the rich fields anyway.

Answer

On the question as asked

02_validator.md is necessary, and it is the highest-value unbuilt thing in the repository.

It is not redundant with the harvesting pipeline, because the harvesting pipeline was explicitly written not to do any of it. It partly overlaps 01_case_finder.md, which has never run and holds zero cases. Today, the number of checks in this system that verify source independence, KPI traceability, or contradictory evidence is zero. The validator is all of them.

What follows from that:

  1. Keep the validator; commit it today. It is 12 KB, uncommitted, on one machine — and it is the only thing between a 100%-self-reported corpus and a Samsung executive deck.
  2. Stop reading "208 verified" as a quality signal. Rename the field if it stays — fetch_status: fetched | snippet_only says what it means and cannot be misread. The current name will mislead a future reader, and the most likely future reader is you.
  3. Write the harvest → validator adapter. This is the real blocker, and it is smaller than it looks.
  4. Expect heavy attrition, and treat that as the system working. With 0 Tier A sources, universal single-sourcing, and 79% missing transformation dates, a faithful run of check 3 (Tier D may never anchor a main-deck claim), check 4, and check 5 will send most of the corpus to appendix or manual_review. A deck of 6–10 main cases from 231 harvested is roughly the expected yield — that is the gate doing its job, not failing.
  5. If you ever run 01_case_finder, revisit this. That is the only scenario where a redundancy argument becomes real — and even then, the quota-versus-audit separation is worth the duplicated effort.
