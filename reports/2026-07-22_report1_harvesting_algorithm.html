1 · Shape

Two harvesters, one shared state directory

Everything runs out of state/. Two independent harvest lanes feed it, and a thin orchestrator sequences them:

scripts/harvest_all.sh          orchestrator — agent → mcp → prompt → skill → ax_cases
   ├─ scripts/harvest_entities.sh <topic> [target]     4 entity topics
   │     └─ scripts/merge_entity_registry.sh  →  state/entity_registry.json
   └─ scripts/harvest_ax_cases.sh [target]
         └─ scripts/merge_ax_case_harvest_registry.sh → state/ax_case_harvest_registry.json

The orchestrator owns ordering, skipping and an honest pass/fail summary. It deliberately runs no stage in the background — the header comment states it outright: “Sequential and bounded: each stage runs to completion before the next starts (no &, no parallelism)”. That is the constraint this report exists to characterise.

2 · The loop

One topic, one iteration, six steps

harvest_entities.sh <topic> <target> closes the gap between the current verified count and the target by repeating a bounded loop. target is a final total, not an amount to add, so an interrupted run resumes naturally from the merged registry count.

1

Candidate sourcing

A claude -p call with Read, WebSearch, WebFetch reads two seeds — the topic’s awesome-list report at reports/awesome-lists/awesome_<topic>.md (plus the raw upstream READMEs it cites, to get past that report’s ~40-row cap) and the search-hit shard state/search_hits_<topic>.json. It returns at most BATCH_SIZE (40) candidates as {hits:[{source_url,target_url,title,snippet,domain}]}.

Three exclusion sets are pushed into the prompt: URLs already entity_extracted:true in the ledger, URLs in this run’s attempted-set, and any target_url already held by an entity in the registry. The last one is what stops the same entity being re-catalogued through a different citing page.

2

Attempted-set + ledger seed

Every source_url sent this loop is unioned into state/harvest_<topic>_attempted.json before the verdict is known — so a rejected candidate is never re-selected later in the same run. A ledger row is then seeded for each new URL in state/visited_url_ledger.json, because the patch in step 5 can only update rows that already exist (unique_by keeps first occurrence).

The ledger dedup key is source_url, not target_url: the ledger’s job is “don’t re-fetch this citing page”. Same-entity dedup is a different guarantee, handled by entity_key at merge time.

3

Deterministic GitHub metadata prefetch

scripts/github_meta.py prefetch resolves star counts and canonical URLs for candidate GitHub repos outside the model, against a persistent cross-run cache (state/github_meta_cache.json, 7-day freshness) and writes a sanitized per-loop file the extractor reads instead of calling api.github.com itself. Authenticated when a token is in the environment; strictly bounded (max_unauth=50) when not. Non-fatal by design — on any failure the extractor still receives valid JSON and github_stars falls back to null.

4

Stage 1G extraction

A second claude -p call, system-prompted from agents/stage1/1G_entity_extractor.md, with only Read, WebFetch. For each candidate it verifies or resolves target_url and pulls the description from that page specifically. description_source:"verified" means exactly that; a description from the citing page or the search snippet alone is snippet-only, and target_url that cannot be resolved is written as the literal string "unknown". Stars are looked up only in the local metadata file, never estimated from a page.

5

Ledger patch + registry merge

The batch’s ledger_patch[] folds entity_extracted/entity_ids back onto the seeded rows, then merge_entity_registry.sh folds the entities into the master registry. Dedup key is entity_key = topic | lowercase(name). On a hit: bump corroboration_count, keep the richer description (verified never downgrades to snippet-only), union related_topics, one-way-backfill target_url and maintainer_or_vendor out of "unknown", and take the newest non-null star count. A conflicting entity_type or a real-vs-real target_url mismatch is never silently overwritten — it lands in conflicting_evidence_log[] for a human. 26 entities currently carry one.

6

Progress accounting and termination

The loop re-tallies verified entities for this topic and stops on the first of: target reached · MAX_LOOPS (40) · NO_PROGRESS_THRESHOLD (3) consecutive loops that added nothing. A single barren batch never halts a run, because the attempted-set grew and the next loop sources different URLs.

The shape of the problem. A loop costs roughly 576 + 522 + 2 + 2 ≈ 1 100 s (~18 min), and 99.6 % of that is network-and-model latency — two blocking claude -p calls. The two steps that actually touch shared state, the prefetch and the merge, take about 4 seconds combined. The lanes are therefore almost perfectly I/O-bound and almost entirely independent: exactly the workload that should run concurrently, and the one place the current design forbids it.

6 · Why it cannot currently run in parallel

Four shared files, three distinct failure modes

Nothing in the loop is CPU-bound and nothing about topic agent depends on topic mcp. The blocker is purely that four lanes would write the same files. Every shared write is a read-whole-file → transform → mv cycle with no lock:

Shared fileWritten byPatternFailure under concurrency
state/entity_registry.jsonevery lane, once per loopjq reads the whole master, writes mktemp, mvLost update. Lane B reads the master before lane A’s mv lands, then overwrites it. A’s whole batch disappears — silently, since the merge reports success and recomputes metadata that looks self-consistent.
state/visited_url_ledger.jsonevery lane, twice per loopsame, but through a fixed temp path $LEDGER.tmpFile corruption. Two lanes write the same .tmp at once → interleaved bytes → invalid JSON, then mv installs it. The jq empty guard catches it and aborts, so the run dies rather than silently corrupting — but it dies. Plus the same lost-update race.
state/github_meta_cache.jsonevery lane, once per loopPython load → atomic_write_jsonCache-entry loss. The write itself is atomic, so no corruption — but a concurrent lane’s newly cached repos are dropped, causing avoidable re-fetches against the 60/hr unauthenticated limit.
tally() reads of the registryevery lane, several times per loopjq read during another lane’s mvTransient mis-read of progress/termination state — can trip a false no_progress increment.

The lost update is the dangerous one. Corruption is loud: jq empty fires and the script exits 1. A lost update is silent — the registry stays valid JSON, the metadata block is recomputed and internally consistent, the merge prints [merge] folded N entities, and the only trace is that a batch that cost ~18 minutes of model time is simply not there. Given that the merge window is ~2 s inside an ~1 100 s loop, the per-loop collision probability with four lanes is low but nonzero, and it compounds: over a 40-loop, 4-lane run it is a near-certainty that at least one batch is silently discarded.

Not blockers

For completeness, these are already correctly sharded and need no change: state/harvest_<topic>_{hits,entity_batch,attempted,raw_*,github_meta}.json, state/harvest_<topic>.err, and the timing log state/logs/harvest_<run_id>.jsonl (run-id includes the PID). The per-topic seed inputs — the awesome-list report and search_hits_<topic>.json — are read-only.

7 · Secondary constraint

Session rate limits

Beyond file contention there is a known external ceiling, recorded from earlier runs: long or concurrent harvests can hit the Claude session rate limit, at which point all in-flight lanes fail their candidate-batch step at the same moment. Any parallel design therefore needs per-lane failure isolation — one lane hitting the ceiling must not take down the run — and a staggered start rather than four simultaneous cold launches.

8 · Conclusion

The algorithm is sound; the storage layout is the bottleneck. Verification discipline, dedup, conflict logging, bounded termination and honest completion checks are all enforced structurally and are working — 975 verified entities with 26 flagged conflicts and zero invented fields. What does not scale is that four independent, 99.6 %-I/O-bound lanes are serialised behind a single mutable registry file and a single mutable ledger. The fix is not to add locking around a shared file but to give each lane a file it exclusively owns, and to reduce the union to a derived artefact produced by a single writer after the lanes finish. That is the subject of Report #2.
